# Documentation

Use short, direct sentences and exact API names. Lead with the reader's action or the system behavior. Follow the Google
developer documentation style guide and use selected Simplified Technical English principles when useful; do not claim
formal compliance. Define uncommon terms, state conditions before dependent actions, and include verification results.
Avoid filler, marketing claims, idioms, and repeated explanations. Simplify language without removing technical detail.
Use relative links and language-tagged code blocks. Follow the current project's terminology when it differs from general
guidance.

Reference docs describe current behavior. Update them in the same change as the behavior. Do not describe milestones,
implementation progress, or past corrections in them: Git history, pull requests, and release notes keep that record.
State validation levels and unsupported capabilities in `docs/compatibility.md`. Put API details in Go doc comments.
